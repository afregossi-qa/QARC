# CSV Export Format Guidelines for QA Test Cases

## Purpose
This document defines the standard CSV format for exporting test cases to TCMS (Test Case Management System). All CSV exports must follow this exact structure.

## CSV Structure

### Column Headers
```
Folder,Requirements,Existing Case ID,Summary,Description,Precondition,Test Steps,Expected Result,Priority,Tags,Automation Status,Status,AI-Automated,AI-Generated
```

### Row Format Rules

1. **First Row (Test Case Header)**
   - Contains ALL test case metadata
   - Folder: Feature folder name (e.g., "POS-9967 - Implement Delta based config download")
   - Requirements: Ticket number (e.g., "POS-9967")
   - Existing Case ID: Test case ID (e.g., "TC-001")
   - Summary: Full test case title with ticket prefix and feature brief using format: `"POS-XXXX | {Feature Brief} : {Test Case Title}"` (e.g., `"POS-9967 | Delta Config Sync : Three-Entity Initial Sync"`)
   - Description: Complete test description including objective, test data, and notes
   - Precondition: All preconditions (bullet list format with " - " prefix)
   - Test Steps: First test step with expected result
   - Expected Result: Overall expected result for entire test case
   - Priority: Priority level (e.g., "Critical", "High", "Medium")
   - Tags: Comma-separated tags (e.g., "POS-9967,DeltaBased,Employees")
   - Automation Status: Automation status (e.g., "To be Automated")
   - Status: MUST be "Published" for all test cases
   - AI-Automated: Whether the test case has AI-driven automation (e.g., "Yes", "No")
   - AI-Generated: Whether the test case was generated by AI (e.g., "Yes", "No")

2. **Subsequent Rows (Test Steps)**
   - Folder: Same as first row
   - Requirements: Same as first row
   - Existing Case ID: Same as first row
   - Summary: Same as first row
   - Description: EMPTY
   - Precondition: EMPTY
   - Test Steps: Next test step with expected result
   - Expected Result: EMPTY
   - Priority: EMPTY
   - Tags: EMPTY
   - Automation Status: EMPTY
   - Status: EMPTY
   - AI-Automated: EMPTY
   - AI-Generated: EMPTY

### Field Formatting

#### Description Field Format
```
{Objective description}

{Additional context or notes}

Test Data:
- {Data item 1}
- {Data item 2}
- {Data item N}
```

#### Precondition Field Format
```
- {Precondition 1}
- {Precondition 2}
- {Precondition N}
```
Note: Use newlines to separate preconditions, each starting with "- " (dash-space)

#### Test Steps Field Format
```
{Action description}
```
Note: Do NOT include "Step {number}:" prefix - just the action description

#### Expected Result Field Format (in Test Steps column)
```
{Expected outcome for this step}
```

#### Tags Field Format
```
{TicketNumber},{Tag1},{Tag2},{TagN}
```
Always include ticket number as first tag, followed by feature-specific tags

### Example Structure

```csv
Folder,Requirements,Existing Case ID,Summary,Description,Precondition,Test Steps,Expected Result,Priority,Tags,Automation Status,Status,AI-Automated,AI-Generated
"POS-9967 - Delta Config Download",POS-9967,TC-001,"POS-9967 | Delta Config Sync : Three-Entity Initial Sync","Verify POS performs full sync for all three entities on fresh startup
```

## Critical Rules

1. **Multi-row per test case**: Each test case spans multiple rows (one per step)
2. **Empty cells**: Subsequent rows have empty Description, Precondition, Expected Result, Priority, Tags, Automation Status, AI-Automated, and AI-Generated
3. **Consistent identifiers**: Folder, Requirements, Existing Case ID, and Summary must be identical across all rows of same test case
4. **Quote wrapping**: Wrap fields containing commas, newlines, or quotes in double quotes
5. **Escape quotes**: Use double quotes ("") to escape quotes within quoted fields
6. **No step numbering**: Do NOT include "Step {number}:" prefix in test steps - just the action description
7. **Expected results**: Include expected result for EACH step in the Test Steps column

## Tags Guidelines

### Standard Tags by Feature
- Delta-based sync: "DeltaBased"
- Employee features: "Employees"
- Shared Employee features: "SharedEmployee"
- Job Title features: "JobTitle"
- Permission cache: "PermissionCache"
- Error handling: "ErrorHandling"
- API validation: "API"
- Configuration: "Configuration"
- Persistence: "Persistence"

### Tag Format
- Always include ticket number as first tag
- Use comma separation without spaces
- Use PascalCase for multi-word tags

## Priority Levels
- Critical: P0 tests that must pass before production
- High: P1 tests that should pass
- Medium: P2 tests that are nice to have

## Automation Status Values
- "To be Automated": Test case planned for automation
- "Automated": Test case already automated
- "Manual Only": Test case cannot be automated

> **IMPORTANT**: These are AIO-compatible values only. Do NOT confuse with the local-only `Automation Status: Required | Manual` and `Regression Potential: High | Medium | Low` tags found in TC headers of `FINAL_TEST_CASES` markdown files. Those local tags are for internal pipeline agents (Validator, Regression Architect, Translator) and must NEVER appear in CSV exports or AIO API calls.

## Status Values
- "Published": REQUIRED for all test cases - makes them visible and ready for execution
- "Draft": Test case still being worked on (DO NOT USE for exports)

## AI-Automated Values
- "Yes": Test case has AI-driven automation scripts generated
- "No": Test case does not have AI-driven automation (default for manual-only tests)

> Populated on the metadata row only. Reflects whether the Automation Pipeline (Architect → Translator → Executor) has produced executable scripts for this test case.

## AI-Generated Values
- "Yes": Test case was generated or substantially authored by AI agents (QA-Expert, QA-Validator pipeline)
- "No": Test case was manually authored by a human tester

> Populated on the metadata row only. Reflects the authorship origin of the test case content.
